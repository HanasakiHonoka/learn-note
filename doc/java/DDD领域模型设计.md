# DDD 领域模型设计

> DDD（Domain-Driven Design，领域驱动设计）是一套围绕业务知识组织软件模型、代码与协作的方法。核心目标是让复杂业务规则有清晰、稳定、可演进的表达，而不是多建几个目录或把所有系统改成微服务。

## 一、先理解 DDD 要解决什么问题

订单系统最初可能只有“保存订单”，后来增加优惠、支付、取消、退款、履约。若规则散落在 Controller、Service、SQL 和定时任务中，同一个业务概念就会出现多套解释：有人认为付款就能发货，有人还要求风控通过；一个入口禁止修改已支付订单，另一个入口却直接更新金额。

DDD 尝试把**业务语言、业务边界和规则的归属**统一起来：

- 与业务人员共同建立模型，用“订单确认”“占用库存”等业务语言讨论需求。
- 明确模型的适用边界，同一个词在不同边界内可以有不同含义。
- 让规则集中在负责它的模型中，调用者通过业务行为修改状态。
- 用清晰的模块边界限制变化的传播，把主要建模投入放在有竞争力的核心业务上。

**领域模型不是数据库表的面向对象翻译。** 它是对特定问题的概念、关系、行为和约束的抽象，既包含结构，也包含业务决策。比如“订单总价等于各明细金额之和”“未支付订单才能取消”比 `order` 表有哪些字段更能决定模型的设计。

### 1. 三个容易混淆的词

| 概念 | 关注点 | 订单示例 |
| --- | --- | --- |
| 领域（Domain） | 要解决的业务问题范围 | 电商交易 |
| 领域模型（Domain Model） | 为解决问题建立的业务抽象 | 订单、明细、金额、取消规则 |
| 领域层（Domain Layer） | 在代码中承载模型与规则的位置 | `Order.cancel()`、`Money`、定价策略 |

领域模型也可以先画在白板上；有一个叫 `domain` 的包不代表已经建立了有效模型。DDD 不专属于 Java，也不要求一定使用面向对象；Java 中常用对象承载状态与行为，也可以用不可变数据和纯函数表达规则。

### 2. 最关键的设计理念：业务不变量

**业务不变量（Invariant）是在规定的一致性边界内必须始终成立的业务约束。** 例如订单明细数量大于零、不同币种不能直接相加、已取消订单不能确认支付。

设计时先问：什么状态绝对不能出现？谁有权改变它？哪些数据必须一起成功或一起失败？这会影响聚合边界、方法接口、事务与并发方案。模型方法能保护单个内存对象，但多请求竞争仍需要数据库版本校验、锁或条件更新；DDD 本身不提供并发正确性。

## 二、战略设计：先把业务边界分清楚

战略设计处理“系统分成哪些部分、各部分采用什么语言、如何协作”；战术设计再处理边界内部的对象、行为和一致性。只使用实体、仓储而不澄清业务边界，容易得到一套结构整齐但仍然耦合的代码。

### 1. 子域与核心投入

| 子域 | 含义 | 可能的例子 | 通常的投入方式 |
| --- | --- | --- | --- |
| 核心域（Core Domain） | 形成业务差异和竞争优势的能力 | 特定平台的履约调度、动态定价 | 深入建模，持续验证，投入主要业务与技术能力 |
| 支撑域（Supporting Subdomain） | 为核心业务服务，通常需要一定定制 | 特定业务的运营配置 | 按实际复杂度实现，避免不必要的抽象 |
| 通用域（Generic Subdomain） | 行业中已有较成熟的通用解法 | 通用认证、邮件投递 | 优先考虑成熟产品、库或外部服务 |

分类取决于业务战略，不是固定的技术分类。例如认证对普通电商可能是通用域，对身份安全产品可能就是核心域。

### 2. 通用语言与限界上下文

**通用语言（Ubiquitous Language）**是业务人员与开发者共同使用、并体现在讨论、文档、测试和代码中的语言。若业务说“关闭订单”，代码却同时出现 `delete`、`invalid`、`cancel` 表示同一动作，团队就应澄清它们是否真的等价。

**限界上下文（Bounded Context）**定义一套模型和语言保持一致的边界。销售上下文中的“商品”关心价格与可售状态，仓储上下文中的“货品”关心库位与出入库，物流上下文中的“包裹”关心重量与运输；它们可以关联同一个商品编号，但不应强迫共用一个包含所有字段和规则的 `Product`。

- **子域是问题空间的业务划分，上下文是解决方案中模型适用的边界。** 两者理想情况下对齐，但存量系统可能存在一个子域跨多个上下文等情况。
- 上下文不是一个实体，也不必等于一个进程、数据库或微服务。可以先在单体中用模块边界实现，再根据组织、部署和伸缩需求拆分。
- 一个上下文内部可以有多个聚合；不能把上下文边界当作单个数据库事务边界。

### 3. 上下文映射：边界之间怎样合作

上下文映射（Context Map）既描述技术接口，也描述上下游责任与团队协作方式。常见方式有：

| 方式 | 思想 | 取舍 |
| --- | --- | --- |
| 防腐层（ACL） | 将外部模型翻译为内部语言，如把渠道状态码翻译为本地支付结果 | 隔离外部变化，但增加转换与维护成本 |
| 开放主机服务 / 发布语言（OHS / PL） | 提供清晰、稳定的公共接口与交换协议 | 便于多个下游接入，需要协议版本和兼容治理 |
| 共享内核（Shared Kernel） | 双方共同维护一小部分模型 | 减少重复，但修改需要协调，范围应尽量小 |
| 遵奉者（Conformist） | 下游直接采用上游模型 | 接入快，但下游受到上游模型与变化的约束 |
| 客户方 / 供应方（Customer / Supplier） | 上游把下游需求纳入计划，双方明确交付责任 | 依赖组织协作，不能仅靠接口声明实现 |

不必消除所有耦合；应让耦合有明确位置、方向和负责人。复制一个外部 DTO 并不自动形成防腐层，关键是语义翻译与规则隔离。

## 三、战术设计：规则由哪些模型承载

### 1. 实体、值对象与聚合

| 构件 | 判断依据 | 示例与设计要点 |
| --- | --- | --- |
| 实体（Entity） | 通过身份与生命周期识别，属性改变后仍是同一个对象 | 订单按 `OrderId` 识别；身份相同不代表字段完全相同 |
| 值对象（Value Object） | 由属性值定义，通常没有独立业务身份 | `Money(100, CNY)`、地址快照；通常设计为不可变，通过替换表达变化 |
| 聚合（Aggregate） | 为维护一组不变量划定的一致性边界 | 订单与订单明细作为整体维护总金额、修改条件等规则 |
| 聚合根（Aggregate Root） | 聚合对外的受控入口，本身也是实体 | 外部调用 `Order.changeQuantity()`，避免绕过订单直接改明细 |

实体的业务身份与 Java 的引用相等、`equals/hashCode` 实现不是同一件事。ORM 代理、尚未分配 ID 的新实体、把可变字段放入哈希计算等情况，都需要单独考虑。

值对象不能只是字段包装：`Money` 应明确币种、精度、舍入和运算规则。Java `record` 只保证组件引用不可重新赋值；如果组件是可变集合，仍需防御性复制，才能避免外部间接修改。

### 2. 聚合边界为什么比类图更重要

以订单为例，订单明细是订单内部成员，通常没有绕过订单独立修改的需求；支付单、库存和客户各自有独立生命周期，不应因为“有关联”就全部装进订单聚合。

聚合的常见设计原则：

1. **围绕必须即时成立的不变量划界，尽量保持小聚合。** 聚合过大会增加加载成本、锁竞争和修改冲突，过小则可能把不可延迟的约束拆散。
2. 外部修改从聚合根进入，不暴露可任意修改的内部集合和通用状态 setter。
3. 跨聚合通常按 ID 关联，避免无意加载、修改整个对象图；按 ID 关联并不是禁止查询时联表。
4. 通常争取一次事务只修改一个聚合，再通过事件或流程协调其他聚合。这是减少耦合的设计指导，不是数据库禁止跨聚合事务的硬性规定。
5. 如果一条规则确实要求多个聚合严格原子变更，应重新审视边界，或明确采用本地事务等一致性方案，不能未经业务同意改成最终一致。

**聚合不是数据库 `GROUP BY`，也不是一组有外键关系的表。** 一个聚合可以映射多张表，同一张宽表也不意味着只有一个聚合。订单中的收货地址快照可以是值对象，客户地址簿中的地址则可能是实体，身份与边界取决于业务用途。

### 3. 服务、仓储、工厂与事件

| 构件 | 负责什么 | 不应承担什么 |
| --- | --- | --- |
| 应用服务（Application Service） | 编排用例、协调权限检查、事务、仓储与外部端口，调用领域行为 | 重复实现属于模型的核心业务规则 |
| 领域服务（Domain Service） | 表达不自然归属某个实体或值对象的业务决策，如跨对象的定价策略 | 接管所有逻辑，变成换了名字的巨型 Service |
| 仓储（Repository） | 从领域视角加载和保存聚合，接口表达领域需要，基础设施负责实现 | 为每张表都机械创建 CRUD 仓储，或负责报表任意查询 |
| 工厂（Factory） | 当创建过程复杂时，构造满足初始约束的对象或聚合 | 每个类都必须配工厂；把后续用例全部塞进创建逻辑 |
| 领域事件（Domain Event） | 表达领域内已经发生的事实，如 `OrderConfirmed` | 把尚未执行的请求伪装成事实，或假设事件对象等于可靠消息 |

应用服务也可以有分支，如“找不到订单就拒绝请求”，不要求它完全没有 `if`。判断依据是：分支在协调一次用例，还是在决定“什么业务状态允许发生”。前者通常放应用层，后者应由模型或领域服务维护。权限涉及的归属、额度等业务规则，也不能只靠入口检查。

领域服务适合无自身业务身份、以行为为中心的操作；优先用参数传入决策所需的事实。需要依赖外部能力时，可以通过抽象端口隔离实现，但要警惕在领域行为中执行远程 I/O 带来的超时与一致性问题。

## 四、常见领域逻辑组织范式及优缺点

### 1. 贫血、充血、失血与胀血

“贫血模型”“充血模型”是常见讨论用语；“失血”“胀血”的定义在不同资料中并不一致。下面用**业务行为放在哪里、技术职责是否混入**来约定比较，避免只争论名称。

| 模型 | 本文约定的含义 | 优点 | 缺点与适用边界 |
| --- | --- | --- | --- |
| 失血模型 | 对象主要是数据容器，几乎没有行为，逻辑全部在对象外 | 结构直接，适合传输数据、简单映射 | 不能靠对象自身保护业务约束；DTO 如此设计很正常，不应强行充血 |
| 贫血模型（Anemic Domain Model） | 对象只有少量校验或简单行为，主要业务规则在 Service 中 | 流程集中、容易配合 CRUD 和 ORM，团队上手快 | 复杂业务易出现规则重复、巨型 Service、任意 setter 导致非法状态 |
| 充血模型（Rich Domain Model） | 状态与相关业务行为封装在模型中，应用服务负责协调 | 不变量集中，语义清晰，规则能脱离 Web/数据库进行测试 | 建模与持久化映射成本较高，需要团队理解一致的边界；简单 CRUD 收益有限 |
| 胀血模型 | 在充血基础上把数据库、HTTP、消息发送、事务编排等也塞进实体 | 表面上一个对象“什么都能做”，调用入口少 | 职责混杂、强耦合、难测试；应把技术副作用和用例协调移到相应边界 |

Fowler 对 Anemic Domain Model 的批评主要针对“付出复杂对象模型和映射成本，却没有得到行为封装的收益”。这不代表所有过程式业务逻辑都不合理，也不代表 DDD 要求 DTO、PO、报表对象都充血。

### 2. 同一条规则，贫血与充血怎样表达

假设规则是“只有草稿订单可以确认，且必须有明细”。以下是说明职责位置的伪代码，省略类型定义：

```text
贫血模型：
OrderService.confirm(id):
    order = dao.find(id)
    校验 order.status == DRAFT
    校验 order.lines 非空
    order.setStatus(CONFIRMED)
    dao.update(order)

充血模型：
ConfirmOrderAppService.confirm(id):
    order = repository.find(id)
    order.confirm()       // 由 Order 检查状态、明细并完成合法转换
    repository.save(order)
```

充血的价值在于不同入口调用同一个业务行为，不必各自复制规则。它并不会自动解决重复请求、并发覆盖或消息丢失，这些仍需要明确的应用和基础设施设计。单纯把 `setStatus(CONFIRMED)` 改名为 `confirm()`，却不维护任何约束，也没有获得完整的行为封装收益。

### 3. Transaction Script、Table Module、Active Record 与 Domain Model

这组概念不能与贫血/充血简单一一对应：事务脚本、表模块、领域模型主要讨论业务逻辑的组织方式，Active Record 还涉及业务对象与持久化的结合方式。它们可以在同一系统的不同模块中并存。

| 范式 | 组织方式 | 优点 | 代价 / 典型场景 |
| --- | --- | --- | --- |
| 事务脚本（Transaction Script） | 按一次业务操作写过程，直接校验、计算和更新 | 简单直接，路径清楚，适合规则较少的业务 | 流程增长后可能复制规则；“事务”不意味着天然具备数据库原子性 |
| 表模块（Table Module） | 以表或记录集合为单位组织逻辑，一次处理一组数据 | 适合批处理、数据集与规则相对统一的操作 | 单个业务对象的身份、行为和生命周期较难表达 |
| 活动记录（Active Record） | 对象代表记录，并提供自身加载、保存、删除等能力 | 少量代码即可完成数据驱动的功能 | 持久化与模型耦合，复杂聚合、替换存储和隔离测试更困难 |
| 领域模型（Domain Model） | 用相互协作的对象表达业务概念、状态和行为 | 适合规则密集、变化频繁、有复杂生命周期的业务 | 需要建模、映射与边界治理，容易因过度抽象增加成本 |

Active Record 可以含有业务行为，不能仅因存在 `save()` 就断定它贫血；有 `save()` 也不自动等于上表约定的胀血。关键是技术耦合是否与复杂度匹配。贫血数据对象加事务脚本，对于简单后台往往是合理选择；复杂订单的写入采用充血模型，查询报表直接读投影，也完全可以共存。

### 4. 面向对象与函数式表达

DDD 不要求所有规则都成为可变对象的方法。例如可以用 `confirm(order, facts) -> newOrder + events` 表达状态转换：输入不可变状态和事实，返回新状态及事件，由外层执行持久化和消息发送。

它有利于重放、并发推理和纯函数测试，但仍需设计身份、上下文、聚合边界和可靠提交；函数散落各处同样会造成规则重复。选择对象行为还是纯函数，取决于语言、团队习惯和问题特点。

## 五、Java 示例：用订单聚合保护业务不变量

下面是一个可独立运行的 **Java 17+** 示例，只展示领域规则，不依赖 Spring、数据库和 MQ。为突出模型，金额使用单一的人民币“分”，真实多币种业务应使用带币种的值对象，明确换算与舍入规则。

本例假设：草稿订单允许为空；确认时必须至少有一条明细；确认后不能再修改明细，取消仅允许草稿或已确认状态。商品单价是已经过应用层可信定价流程得到的快照，不能直接采用客户端提交的价格。

```java
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

public class DddOrderExample {
    // 值对象：不暴露 setter，运算产生新值；检测整数溢出。
    record Money(long fen) {
        Money {
            if (fen < 0) throw new IllegalArgumentException("金额不能为负");
        }

        Money add(Money other) {
            Objects.requireNonNull(other);
            return new Money(Math.addExact(fen, other.fen));
        }

        Money multiply(int quantity) {
            if (quantity <= 0) throw new IllegalArgumentException("数量必须为正");
            return new Money(Math.multiplyExact(fen, quantity));
        }
    }

    // 明细没有独立修改生命周期，本例将它作为聚合内的不可变值对象。
    record OrderLine(String skuId, Money unitPrice, int quantity) {
        OrderLine {
            if (skuId == null || skuId.isBlank()) {
                throw new IllegalArgumentException("SKU 不能为空");
            }
            Objects.requireNonNull(unitPrice);
            if (quantity <= 0) throw new IllegalArgumentException("数量必须为正");
            unitPrice.multiply(quantity); // 创建时就校验金额乘法不会溢出。
        }

        Money subtotal() {
            return unitPrice.multiply(quantity);
        }
    }

    enum OrderStatus { DRAFT, CONFIRMED, PAID, CANCELLED }

    // 聚合根：只提供有业务含义的状态转换，不提供 setStatus。
    static final class Order {
        private final String id;
        private final List<OrderLine> lines = new ArrayList<>();
        private OrderStatus status = OrderStatus.DRAFT;

        Order(String id) {
            if (id == null || id.isBlank()) {
                throw new IllegalArgumentException("订单 ID 不能为空");
            }
            this.id = id;
        }

        void addLine(String skuId, Money unitPrice, int quantity) {
            requireStatus(OrderStatus.DRAFT);
            OrderLine line = new OrderLine(skuId, unitPrice, quantity);
            total().add(line.subtotal()); // 先校验总额，成功后再改变内部状态。
            lines.add(line);
        }

        Money total() {
            Money sum = new Money(0);
            for (OrderLine line : lines) sum = sum.add(line.subtotal());
            return sum;
        }

        void confirm() {
            requireStatus(OrderStatus.DRAFT);
            if (lines.isEmpty()) throw new IllegalStateException("空订单不能确认");
            status = OrderStatus.CONFIRMED;
        }

        void markPaid(Money paidAmount) {
            requireStatus(OrderStatus.CONFIRMED);
            if (!total().equals(Objects.requireNonNull(paidAmount))) {
                throw new IllegalArgumentException("支付金额与订单金额不一致");
            }
            status = OrderStatus.PAID;
        }

        void cancel() {
            if (status != OrderStatus.DRAFT && status != OrderStatus.CONFIRMED) {
                throw new IllegalStateException("当前状态不能取消");
            }
            status = OrderStatus.CANCELLED;
        }

        List<OrderLine> lines() {
            return List.copyOf(lines); // 集合与明细均不能由调用方修改。
        }

        private void requireStatus(OrderStatus expected) {
            if (status != expected) throw new IllegalStateException("订单状态不匹配");
        }
    }

    public static void main(String[] args) {
        Order order = new Order("order-1001");
        order.addLine("sku-1", new Money(1990), 2);
        order.confirm();
        order.markPaid(new Money(3980));
        System.out.println(order.id + ": " + order.status + ", " + order.total().fen() + " 分");
    }
}
```

运行结果为 `order-1001: PAID, 3980 分`。`OrderLine` 在需要独立跟踪明细、售后或部分发货时也可能设计成有 `lineId` 的实体，不能把这里的简化建模当作固定模板。

`markPaid()` 表达的是本地订单的业务转换。调用前仍应由适配器验签、应用流程核对支付单归属与渠道流水，并只接受可信支付结果；订单对象不能自行证明钱已到账。示例没有实现支付单、退款、重复通知幂等或并发控制，也没有把这些能力隐藏在一个 setter 中。

## 六、Java 工程中如何落地

### 1. 按业务模块组织，再在模块内部表达职责

下面是一种可选结构，目录不是 DDD 的强制规范。小项目可以合并目录，关键是依赖与职责清晰。

```text
com.example.trading.order
├── interfaces                 # HTTP、消息消费等入口与协议转换
│   └── OrderController
├── application                # 用例编排与事务协调
│   └── ConfirmOrderAppService
├── domain
│   ├── model                  # Order、OrderLine、Money
│   ├── service                # 确实不能归属某个对象的业务行为
│   └── repository             # OrderRepository 抽象
└── infrastructure
    ├── persistence            # 数据映射、仓储实现、乐观锁
    └── integration            # 外部支付、消息投递等适配器
```

典型依赖关系为：入口依赖应用层，应用层使用领域模型与所需端口，基础设施实现这些端口；领域模型不依赖 Controller、Mapper、HTTP SDK。接口应放在需要该抽象的一侧：仓储通常归领域，纯用例协调的通知端口也可以归应用层，不必把所有接口都塞进领域层。

这与六边形 / 整洁架构强调的依赖向内兼容，但 DDD 并未规定唯一的四层目录结构。传统分层也可以承载 DDD，前提是核心业务规则的归属和模型边界足够清楚。

### 2. 一次用例的调用与提交顺序

下面是省略类型定义的流程伪代码；事务开始与提交要由真实框架或事务管理器执行：

```text
确认订单用例：
    从认证上下文获取操作者，校验其操作权限
    开启本地事务
        通过仓储加载订单及必要明细，取得版本号 v
        校验订单归属等业务规则
        调用 order.confirm()
        仓储保存聚合：以 version = v 为条件更新，成功后版本加一
        写入 OrderConfirmed 对应的 outbox 记录
    提交事务
    后台投递器读取 outbox，可靠投递事件并记录进度
```

应用层划定事务边界，仓储实现执行版本条件写入。更新影响行数为零时，应回滚并处理并发冲突，不能继续写明细或把事件当成已提交。Spring 中要保证 `@Transactional` 通过有效代理调用，不能假设同类内部调用也会触发事务；若使用受检异常，还应配置符合用例要求的回滚规则。

### 3. 领域事件不等于 MQ 消息

- **命令**表达请求，如 `ConfirmOrder`；**事件**表达已发生事实，如 `OrderConfirmed`。事件应带稳定的事件 ID、业务 ID、发生时间等信息，必要时带聚合版本供下游判断顺序。
- 领域事件可以只在进程内使用，不必全部发送 MQ。跨上下文的集成事件应使用明确、可演进的协议，避免直接序列化内部实体并泄露整个对象图。
- 调用实体方法后立刻发 MQ，再保存数据库，可能出现“消息已发但数据库回滚”；提交数据库后直接发 MQ，也可能在提交与发送之间宕机。
- 需要可靠发布时，可以把聚合变更与 outbox 同事务落库，再由投递器重试。投递仍可能重复，下游需要幂等、乱序处理、失败重试与对账。
- `@TransactionalEventListener(AFTER_COMMIT)` 可安排提交后的进程内处理，但单靠它没有持久化重试保证，不能替代可靠 outbox。

### 4. 持久化与并发不会因为充血而消失

MyBatis 可以将持久化对象（PO）映射成聚合；JPA 也可以直接映射带行为的实体。是否分离领域对象和 ORM 对象，取决于映射复杂度、框架侵入与维护成本，分离会增加转换代码，并非越多越好。

- DTO 服务于接口传输，PO 服务于存储，领域对象服务于规则表达；用途可以区分，但不必机械地为每张表复制三套结构。
- 从存储重建聚合与“创建一张新订单”语义不同。重建不应重复产生创建事件；应校验必要约束，并处理历史数据或规则版本差异。
- 并发确认、支付和取消可能同时读取同一状态，需要乐观锁、悲观锁或原子条件更新保证只有合法变更提交。对象里的 `if` 不能跨线程、跨进程互斥。
- 数据库唯一键、非空与检查约束等仍是重要防线；复杂不变量需要结合事务、隔离级别与业务协议保证，不能只写在注释里。
- 不必为一次报表查询加载完整聚合，可以直接查询 DTO / 投影。聚合主要保护写入一致性，不要求所有读操作都经过它。

## 七、与其他工程设计思想的区分

这些概念跨越不同层次，不能全部看成互斥的“同级架构”。与 DDD 直接比较时，要先明确是在比较建模方法、业务逻辑组织方式、代码依赖结构，还是部署形态。

| 概念 | 主要回答的问题 | 与 DDD 的关系与区分点 |
| --- | --- | --- |
| 数据驱动 / CRUD 设计 | 如何围绕表与增删改查快速实现功能？ | 简单业务成本低；DDD 更强调业务语义、边界和不变量，仍然需要数据库设计 |
| 事务脚本 | 一次业务操作的逻辑怎样集中组织？ | 是领域模型的常见替代方案；一个上下文可根据复杂度选择，不必全面使用充血模型 |
| 面向对象设计（OOD） | 对象的职责、封装、协作怎样安排？ | 是实现模型的常用手段；DDD 还覆盖通用语言、上下文和业务协作，不等于 OOD 全集 |
| GoF 设计模式 | 如何复用策略、创建、适配等局部代码协作方案？ | 属于更局部的工具；DDD 的仓储、聚合等模式主要围绕领域与一致性，可与策略模式等组合 |
| MVC | 视图、控制与模型怎样分工？ | MVC 的 Model 范围依具体框架而异，不必就是 DDD 领域模型；Spring MVC 控制的是 Web 入口 |
| 三层 / 分层架构 | 表示、业务、数据访问怎样组织？ | 是职责与依赖划分；Service 层可以采用事务脚本，也可以编排充血领域模型 |
| 六边形 / 整洁架构 | 如何通过端口、适配器和向内依赖隔离外部技术？ | 与 DDD 互补；内部业务可以采用领域模型，也可以采用较简单的用例逻辑 |
| 微服务 / SOA | 能力怎样划分、部署、通信和治理？ | 侧重服务边界与运行方式；上下文可为拆分提供依据，但上下文不必与服务一一对应 |
| CQRS | 写命令和读查询是否采用不同模型？ | 可用于复杂写规则与高效查询；不要求两个数据库、不要求微服务，也不自动意味着异步 |
| 事件驱动架构（EDA） | 组件如何基于事件协作？ | 可承载上下文间协作；DDD 可以没有 MQ，事件驱动系统也未必采用 DDD |
| 事件溯源（Event Sourcing） | 是否把事件序列作为权威状态来源？ | 可重放恢复状态，但引入事件版本、重放、副作用与投影成本；与 DDD、CQRS 均可独立采用 |

例如，“采用分层架构的模块化单体，核心订单使用 DDD 充血模型，查询直接读投影”是自洽的方案。是否进一步采用微服务、CQRS 或事件溯源，需要独立论证，不能因为使用 DDD 就默认全部引入。

## 八、跨聚合协作与一致性取舍

下单、扣库存、支付往往跨越多个聚合甚至上下文。DDD 帮助识别规则归属，但不会让分布式调用成为一个本地事务。

以订单和库存为例，可以先创建“待库存确认”的订单，可靠发送库存预留请求；库存按业务键幂等预留，成功后订单进入可支付状态，失败则拒绝或关闭。每一步必须有可持久化状态、超时处理和恢复路径。库存聚合自己保护“不超卖”，订单自己保护“未确认库存不可付款”。

如果业务要求协调多步操作，可用流程管理器或 Saga 维护进度与补偿；补偿是业务操作，不是把历史当作没有发生。例如支付成功后的补偿可能是发起退款，退款也可能失败，必须能重试、对账或人工处理。

| 需求 | 常见选择 | 必须说明的代价 |
| --- | --- | --- |
| 单个聚合内强一致 | 本地事务 + 并发控制 | 热点聚合可能竞争严重 |
| 同库多个聚合必须原子变更 | 显式本地事务，并复核聚合边界 | 增加耦合与锁范围，后续拆分更难 |
| 跨上下文允许短暂中间状态 | 可靠事件 + 幂等 + 流程协调 | 需要处理超时、失败、补偿、观测和对账 |
| 跨系统必须同步原子提交 | 评估分布式事务协议或调整业务流程与边界 | 协调与故障恢复复杂，影响可用性和性能 |

不要把“最终一致”当成失败后不处理，也不要为了避免分布式事务而擅自放宽资金、库存等业务约束。

## 九、什么时候值得用 DDD，什么时候应该简化

DDD 的主要收益是降低复杂业务长期变化的成本，代价是学习、协作、建模、持久化映射与边界维护。它不是性能优化技术，也不保证开发初期更快。

| 业务情况 | 建议 |
| --- | --- |
| 规则密集、生命周期复杂，多入口必须遵守同一规则 | 优先在核心写入流程应用领域模型，明确不变量与聚合 |
| 多团队协作，同名概念含义不同、跨模块变化频繁 | 优先做战略设计、通用语言和上下文边界，避免先纠结目录 |
| 简单字典管理、低变化后台、数据搬运 | CRUD / 事务脚本通常更经济，不必为每个字段设计值对象 |
| 报表、搜索、数据分析 | 优先按查询需求建模，不必完整加载写模型 |
| 团队对业务认识不足或遗留系统很大 | 先选择一个高价值用例，与业务共同验证，逐步提炼和迁移 |

**局部采用比全量套模板更常见。** 核心交易域可以用充血模型，运营配置用 CRUD，报表用 SQL；它们都应保持明确边界，不需要为了“统一”而付出相同复杂度。

## 十、建模步骤、常见误区与验证

### 1. 从业务场景走到代码

1. 选一个具体用例，梳理参与者、命令、已发生事件与失败分支；可以通过事件风暴等协作方式与领域专家一起讨论。
2. 建立词汇表，澄清同名异义与状态含义，划分子域和上下文，画出依赖方向。
3. 列出不变量及一致性要求，再决定实体、值对象与聚合边界，不要直接按数据库外键画大对象图。
4. 让模型提供有业务含义的行为，应用层编排事务、仓储与外部能力；通过一个完整用例检验职责是否自然。
5. 推演重复请求、并发修改、回滚、外部超时与消息重复，补齐幂等、版本控制和恢复协议。
6. 用真实业务变化检验模型：新增规则时，是否能集中修改对应责任，而不是同时修改多个入口？持续调整边界与语言。

### 2. 常见误区

| 误区 | 更合适的理解 |
| --- | --- |
| 表名就是实体名，外键决定聚合 | 业务身份与不变量决定模型，表结构服务于持久化 |
| DDD 必须微服务、MQ、CQRS、事件溯源 | 这些是可组合且各有成本的独立决策 |
| 所有 Service 逻辑都应搬到实体 | 区分领域决策、用例协调与技术副作用，避免胀血 |
| 有领域服务就不需要实体行为 | 自然属于某个实体的规则应就近封装，避免所有规则集中在服务 |
| 富模型一定比贫血模型好 | 看业务复杂度、变化频率与团队能力，简单流程优先保持简单 |
| 定义几个空接口就实现了依赖倒置 | 接口应代表实际的业务或用例需要，并隔离会变化的外部实现 |
| 领域事件发布成功就代表业务提交成功 | 必须明确事务提交点与可靠投递、消费协议 |
| 用内存状态检查就能保证并发正确 | 必须由持久化层配合事务和并发控制保证提交结果 |

### 3. 怎样验证模型是否有效

优先验证业务规则与边界：空订单不能确认、确认后不能改明细、金额不匹配不能标记支付、取消后不能支付、外部不能修改内部集合。可使用纯领域单元测试，不必启动 Spring。

再用仓储集成测试验证往返映射、事务回滚和版本冲突；对跨系统流程验证重复事件、乱序、宕机恢复和补偿。不要只断言 getter 返回某个字段；真正重要的是“不允许的状态无法提交，允许的流程能完成”。

## 十一、面试中怎样回答

**什么是 DDD？** 围绕业务知识建立通用语言、模型边界和业务规则的方法。战略设计关注子域、上下文和协作，战术设计关注实体、值对象、聚合、服务、仓储与事件。目标是控制复杂业务变化，而不是增加技术组件。

**贫血和充血的核心区别？** 主要看业务规则是否与相关状态封装在一起。贫血模型把主要规则放在外部 Service，简单 CRUD 成本低；充血模型通过业务行为保护不变量，适合复杂生命周期，代价是建模与映射成本。两者都需要事务、并发和幂等设计。

**DDD 与设计模式、微服务是什么关系？** DDD 是业务建模与协作方法，GoF 模式提供局部代码组织工具，微服务是服务拆分与部署方式，层次不同。可以在单体中实践 DDD，也可以把没有领域模型的 CRUD 应用部署成微服务。

**怎么判断聚合划得是否合适？** 先看必须在同一次提交后成立的不变量，再看生命周期、修改入口、并发冲突和加载成本。若总要跨聚合强一致更新，或一次修改要加载大量无关对象，就应重新检查边界。
