# 数据库常见面试题（MySQL）

本文以 MySQL 8.0/8.4 的 InnoDB 为主要背景，整理后端开发面试中的常见问题。**高频**表示近期多份面试题资料反复涉及、建议优先掌握；**低频**表示相对偏深入或依赖岗位场景，并非不会被问到。标签是基于文末资料的定性整理，不是统计结果，实际频率会随岗位、级别和项目变化。SQL 编写练习见 [SQL 语法与面试题](sql.md)，更多基础知识见[数据库笔记](db.md)。

## 索引与查询

### 1. 【高频】为什么 InnoDB 常用 B+ 树索引？

B+ 树是多路平衡树，树高通常较低；非叶子节点主要用于导航，叶子节点有序，便于范围扫描和排序。相较哈希结构，它还能支持范围查询和部分前缀查询。索引会占空间并增加写入维护成本，应按实际查询建立，而不是越多越好。

### 2. 【高频】聚簇索引、二级索引、回表和覆盖索引是什么？

InnoDB 的聚簇索引叶子节点保存行数据，通常以主键组织；没有主键时会选择合适的非空唯一索引，否则生成隐藏行 ID。二级索引记录包含索引列和主键值；需要其他列时通常根据主键再访问聚簇索引，即回表。如果索引已包含查询所需的列，可以使用覆盖索引减少回表。主键过宽会增加所有二级索引的空间成本。

### 3. 【高频】联合索引的最左前缀是什么？范围查询之后的列一定无效吗？

索引 `(a, b, c)` 按 a、b、c 的顺序组织，通常能用于按 `a`、`(a,b)` 或 `(a,b,c)` 查询；只按 `b` 查询通常无法直接利用完整的最左前缀。对于 `a = ? AND b > ? AND c = ?`，构造连续扫描范围时通常到 b 的范围条件为止，但 c 仍可能用于索引条件下推、过滤或覆盖查询。优化器在特定条件下也可能使用 skip scan，不能把经验规则当成绝对结论；以执行计划和实测为准。

### 4. 【高频】哪些情况可能导致索引没有被有效使用？

常见情况包括前导通配符 `LIKE '%abc'`、对索引列进行函数或运算、某些隐式类型转换、不符合联合索引前缀，以及返回比例过高时优化器认为全表扫描更便宜。特殊索引、优化器版本和数据分布会影响结果，应检查 `EXPLAIN`，不能一概说这些条件必然失效。日期查询常改为半开区间：

```sql
WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'
```

### 5. 【高频】如何排查慢 SQL？怎么看执行计划？

先结合慢查询日志、调用链和业务参数确认高耗时语句及影响范围；再用 `EXPLAIN` 查看访问方式 `type`、实际选择的 `key`、估算扫描行数 `rows` 和 `Extra` 等，并结合表大小、数据分布、索引和排序分析。必要时用 `EXPLAIN ANALYZE` 对比实际行数与耗时，它会执行语句，应在合适环境和负载下使用。优化查询、索引或数据访问量后，使用代表性参数复测并关注写入和存储成本。

### 6. 【高频】深分页为什么慢？如何优化？

`LIMIT 100000, 20` 通常仍需访问并跳过前面的大量记录。若业务只需顺序翻页，可用游标分页，例如按唯一且稳定的 `id` 排序，下一页查询 `WHERE id > ? ORDER BY id LIMIT 20`。非唯一排序应追加唯一键并构造对应的复合游标。它不适合任意跳页；并发插入、删除和排序字段更新下需明确一致性要求。

### 7. 【低频】索引下推（ICP）是什么？

存储引擎在扫描二级索引时，先用索引中可判断的条件过滤，再对剩余记录回表，减少回表次数。它不是所有查询都适用；执行计划中出现 `Using index condition` 时表示使用了 ICP。

## 事务与并发

### 8. 【高频】事务的 ACID 是什么？

原子性：事务内的操作作为整体提交或回滚；一致性：事务使数据从一个满足约束的状态转移到另一个满足约束的状态，仍依赖业务逻辑与约束设计；隔离性：并发事务的可见性和相互影响受隔离级别控制；持久性：成功提交的数据在符合配置和硬件假设时可在故障后恢复。InnoDB 利用 undo log、redo log、MVCC 和锁等机制共同提供保障。

### 9. 【高频】四种隔离级别及脏读、不可重复读、幻读是什么？

脏读是读到其他事务未提交的数据；不可重复读是同一事务重复读取同一记录时，因其他事务提交更新而读到不同值；幻读通常指重复按条件查询时，因其他事务插入或删除符合条件的行而使结果集合变化。

| 隔离级别 | 标准层面的典型现象 |
| --- | --- |
| 读未提交（RU） | 可能脏读、不可重复读、幻读 |
| 读已提交（RC） | 避免脏读；可能不可重复读、幻读 |
| 可重复读（RR） | 避免脏读、不可重复读；标准仍允许幻读 |
| 串行化（Serializable） | 避免上述现象，并发成本通常更高 |

InnoDB 默认 RR；其快照读与锁定读有各自的防幻读机制，不能简单套用标准表格断言所有具体场景。

### 10. 【高频】MVCC、Read View、快照读和当前读的关系？

MVCC 使用记录版本和 Read View 判断可见性；历史版本通过 undo log 形成版本链。RC 下每次一致性读通常生成新的 Read View；RR 下普通一致性读通常复用事务中首次一致性读创建的 Read View（显式一致性快照等情形需另论）。普通 `SELECT` 通常是快照读；`SELECT ... FOR UPDATE`、`UPDATE` 等使用当前数据并加锁。快照读可保持同一视图，RR 下范围锁定读可用 next-key lock 阻止范围内的插入；混用读和写仍可能看到不同状态，不能说所有业务幻读都被完全消除。

### 11. 【高频】行锁、间隙锁、next-key lock 是什么？

记录锁锁定索引记录；间隙锁锁定索引记录之间的间隙，主要阻止其他事务向该间隙插入；next-key lock 包含记录锁及其前方间隙锁。RR 下锁定读、更新和删除的锁范围取决于索引、查询条件及实际扫描范围：命中唯一索引的唯一记录时通常只需记录锁，范围扫描可能使用间隙锁或 next-key lock。RC 下一般不使用间隙锁，但外键和唯一性检查等仍有例外。没有合适索引可能扫描并锁住大量记录。

### 12. 【高频】死锁如何产生、排查和减少？

两个事务以不同顺序持有并等待彼此需要的锁，就可能形成循环等待。InnoDB 检测到死锁时通常会选择一个事务回滚；应用应对可重试操作做有限次数重试。可用 `SHOW ENGINE INNODB STATUS` 的最近死锁信息及 Performance Schema 锁信息分析；通过统一访问顺序、缩短事务、建立合适索引和减小锁范围降低发生概率，不能保证彻底消除。

### 13. 【高频】如何防止并发扣库存超卖？

将检查和修改合并为一条原子更新，再判断影响行数：

```sql
UPDATE products SET stock = stock - 1
WHERE id = ? AND stock > 0;
```

影响 1 行表示扣减成功，0 行表示库存不足或商品不存在。订单创建与扣减若需原子性，应在同一数据库事务中处理；请求重试还需要业务幂等键和唯一约束，避免重复扣减。

### 14. 【低频】乐观锁和悲观锁如何选择？

乐观锁常用版本号条件更新，如 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`，再检查影响行数；冲突少时适合，但冲突多会增加重试。悲观锁如事务内 `SELECT ... FOR UPDATE`，先锁定再处理，适合冲突较多且需要串行化操作的场景，但要控制事务时长。MVCC 与应用层版本号乐观锁不是同一概念。

## 日志、高可用与实践

### 15. 【高频】undo log、redo log 和 binlog 有什么区别？

undo log 用于事务回滚和构造历史版本；InnoDB redo log 记录页修改相关的重做信息，用于崩溃恢复；MySQL server 层的 binlog 记录数据库变更，用于复制和基于时间点的恢复。redo 与 binlog 的协调提交用于崩溃后保持两者一致。持久性取决于 `innodb_flush_log_at_trx_commit`、`sync_binlog`、存储设备等配置，不能简单认为每次提交都必然已安全落盘。

### 16. 【高频】主从复制和读写分离有什么问题？

主库生成 binlog，从库接收并重放；异步复制可能有延迟，刚写入的数据从从库读取时可能尚不可见。按业务选择写后读主、等待副本追上指定位置或其他一致性方案；主库故障切换时还需考虑未复制事务丢失、故障检测与切换。复制不是备份，误操作也可能被复制，应单独验证备份与恢复。线上排障步骤见下文“线上主从延迟排查”一节。

### 17. 【高频】InnoDB 和 MyISAM 有什么区别？

InnoDB 支持事务、崩溃恢复、外键和行级锁，是现代 MySQL 常用默认引擎；MyISAM 不支持事务和外键，使用表级锁。不同负载下性能取决于数据、查询和配置，不能笼统断言某个引擎总是更快。

### 18. 【低频】大表变更如何降低风险？

先确认 MySQL 版本、具体 DDL 支持的算法和锁级别，以及磁盘空间、复制延迟和回滚方案；在线 DDL 也可能等待元数据锁，并非完全无阻塞。先在接近生产的数据量上演练，监控长事务和复制延迟，在合适时段执行；必要时评估在线变更工具并验证其约束。

### 19. 【低频】什么时候考虑分库分表？带来什么代价？

单机容量、写入或运维窗口成为瓶颈，且索引、SQL 优化、归档和扩容不足时，才评估拆分。拆分后跨分片 JOIN、排序分页、唯一约束、事务、扩容和数据迁移都会更复杂；分片键应结合访问模式和数据分布选择，避免热点。

### 20. 【低频】长事务为什么有风险？

长事务可能持有锁导致等待或死锁，也可能保留旧 Read View，使仍可能被访问的历史版本无法及时清理，增加 undo 空间与清理压力。排查时结合事务运行时间、锁等待与业务调用链；避免在事务中执行不必要的远程调用和长时间等待。

## 线上主从延迟排查

### 21. 【高频】线上出现主从延迟，如何排查原因并解决？

面试时可以按 **确认业务影响 → 保护关键读请求 → 区分接收与回放瓶颈 → 定位根因 → 验证追平并复盘** 的顺序回答。以下以 MySQL 8.0/8.4 的常规 binlog 复制为例，多源复制需要按复制通道分别检查；Group Replication 等架构需结合其专用指标分析。

#### 21.1 先理解延迟发生在哪个阶段

```text
主库事务提交并写入 binlog
    → 从库接收线程（I/O / receiver）拉取 binlog
    → 写入本地 relay log
    → 从库回放线程（SQL / applier，可能包含多个 worker）执行并提交
    → 新发起的查询可见
```

延迟通常分为两类：**日志没有及时到达从库**，或者 **日志已经到达但没有及时执行完成**。即使复制已追平，应用在 RR 长事务中继续使用旧快照，也可能读不到刚提交的数据，不能把所有“读到旧数据”都归因于复制延迟。

#### 21.2 确认影响范围，并先做业务止损

- 确认是单个副本、单个通道还是全部副本延迟；结合告警、订单等业务反馈、发布时间、批处理与 DDL 时间线判断是突发问题还是长期容量不足。
- 对订单状态、余额等需要读到最新提交结果的请求，临时路由到主库或经过确认的健康副本，并评估主库剩余容量，配合限流、缓存和非核心功能降级，避免流量切换压垮主库。
- 降低或暂停可延后的批量写入、离线报表和大规模变更，让复制获得追赶空间；保留现场指标、错误和事务信息，再实施变更。
- 排除有意配置的延迟复制（如 `SQL_Delay`），避免将预期行为当作故障。

#### 21.3 第一步：检查复制是否正常，以及积压发生在哪一段

在从库检查状态，并间隔采样，观察趋势而非只看一个瞬时值：

```sql
SHOW REPLICA STATUS\G
-- 多源复制时指定实际通道：
-- SHOW REPLICA STATUS FOR CHANNEL 'channel_name'\G
```

`SHOW REPLICA STATUS` 从 MySQL 8.0.22 开始提供；更早版本使用 `SHOW SLAVE STATUS`，部分字段也使用旧名称（如 `Slave_IO_Running`）。以下使用较新版本的名称。

| 观察项 | 排查思路 |
| --- | --- |
| `Replica_IO_Running`、`Replica_SQL_Running` | 是否正常运行；I/O 处于连接中、线程停止或报错时，应先处理连接或复制错误，不能只当作“速度慢” |
| `Last_IO_Error`、`Last_SQL_Error` | 检查网络、认证、主库 binlog 缺失，以及重复键、记录不存在、DDL 不兼容等错误 |
| `Source_Log_File` / `Read_Source_Log_Pos` 与 `Relay_Source_Log_File` / `Exec_Source_Log_Pos` | 分别反映接收到和已执行到的源 binlog 位置；要结合文件名、持续采样以及主库当前位置判断，不能跨文件直接相减 |
| `Retrieved_Gtid_Set`、`Executed_Gtid_Set` | 开启 GTID 时，辅助区分已接收和已执行的事务；多源环境下已执行集合可能包含其他通道或本地事务，不能简单比较集合大小 |
| `Relay_Log_Space` | 持续增长可能说明回放跟不上，但它包含 relay log 文件占用，受清理与保留行为影响，不能直接当作精确待回放字节数 |
| `Seconds_Behind_Source` | 作为延迟线索，必须结合线程状态、位点和业务探针判断，不能作为唯一健康标准 |

**为什么不能只看 `Seconds_Behind_Source`？** 它主要反映回放相对接收进度的时间差，不等于某笔业务写入到从库可见的端到端耗时。接收线程落后主库而回放线程已处理完本地日志时，也可能显示 0；线程未运行等状态下可能显示 `NULL`，这不表示没有延迟。并行回放和时钟变化也会影响解读。

进一步结合主库当前 binlog 位点或已执行 GTID 集合判断：

- **主库持续前进，从库接收位置落后且推进慢**：优先检查主库发送能力、网络和从库接收/写 relay log 的能力。
- **从库接收持续推进，但执行位置明显落后**：优先检查回放错误、锁等待、大事务、worker 利用率与资源瓶颈。
- **位点已追平但业务仍读到旧数据**：核对实际路由的副本、连接池、缓存、事务快照和复制过滤配置。

可增加专用心跳表，由主库定期更新，从库读取更新时间，衡量业务可见的新鲜度。注意探针本身的调度间隔、主从时钟同步、查询是否使用新快照，以及心跳表是否被复制过滤；心跳不能替代复制状态和错误监控。

#### 21.4 第二步：查看回放线程、锁和系统资源

以下查询应在出现问题的从库执行，并按通道、worker 和事务关联分析：

```sql
-- 接收连接与各回放 worker 的状态、错误等信息
SELECT * FROM performance_schema.replication_connection_status\G
SELECT * FROM performance_schema.replication_applier_status_by_worker\G
SELECT * FROM performance_schema.replication_applier_status_by_coordinator\G

-- 查看线程正在执行什么、是否等待锁或提交
SHOW FULL PROCESSLIST;
SELECT * FROM information_schema.innodb_trx\G
SELECT * FROM performance_schema.data_lock_waits\G
SELECT * FROM performance_schema.metadata_locks
WHERE LOCK_STATUS = 'PENDING'\G
```

结合 worker 的 `THREAD_ID`、`performance_schema.threads`、锁持有者与业务会话，定位到底是谁阻塞了谁。元数据锁等待还需继续查找对应对象上的已授予锁；不能看到长查询就直接认定它是阻塞者。部分采集项依赖 Performance Schema 配置和账号权限。

同时检查 CPU 使用率、磁盘延迟/IOPS/吞吐与剩余空间、网络带宽/重传、内存与 swap，以及主从配置差异。判断是单个 worker 执行很久、多个 worker 等待同一事务，还是所有 worker 都被资源限制；线程数多并不等于有效并行度高。

#### 21.5 常见原因、证据和对应处理

| 可能原因 | 常见证据 | 解决方案与注意点 |
| --- | --- | --- |
| 网络抖动、带宽不足或跨地域链路问题 | 接收位点落后，I/O 重连、网络重传或带宽饱和 | 修复链路、网络策略与连接问题，评估带宽和复制拓扑；压缩需结合版本、带宽收益和 CPU 成本实测 |
| 主库写入突增、批量导入 | 写入量/binlog 生成速率上升，多个副本同时积压 | 对批任务限速、错峰执行，减少无效写入；扩容并提升回放能力。增加只读副本主要分担读流量，不能直接提高某个副本的回放速度 |
| 大事务或长时间运行的 DDL | 某个事务回放时间很长，其他 worker 等待，延迟突增 | 在源头把可拆分的大批量更新/删除改成小批次提交，控制每批行数和耗时；DDL 提前演练并控制执行窗口。单个事务通常不能靠增加 worker 拆开回放，已经接收到的大事务也不会因此自动变小 |
| 从库查询或本地事务阻塞回放 | `data_lock_waits`、元数据锁或线程状态显示回放被阻塞 | 找到持锁会话，协调提交、回滚或终止；限制从库本地写入和长事务。普通一致性读通常不持有记录锁，但长查询/长事务可能持有元数据锁并阻塞 DDL；终止事务还可能带来较长回滚时间 |
| 从库资源不足或报表争抢资源 | 磁盘延迟高、CPU 饱和、swap、缓存命中下降，报表高峰与延迟重合 | 优化或迁移报表、降低读流量，提升存储/CPU/内存与容量；核对主从硬件和配置，避免副本明显弱于主库 |
| 回放并行度不足或事务依赖强 | 可用 worker 少，或很多 worker 等待热点事务/前序事务提交 | 核对 `replica_parallel_workers` 和对应版本的并行复制配置，逐步调整并压测；并行度受依赖信息、热点行、提交顺序和资源约束，不能无限增加。旧版 8.0 参数名可能以 `slave_` 开头，主库依赖跟踪相关参数在 8.4 有变化，不能直接照搬旧配置 |
| 缺少主键/合适索引或主从表结构漂移 | 行事件回放定位记录成本高，或出现结构相关错误 | 检查表主键、索引与主从结构；按变更流程补充合适的主键/索引并修复结构漂移，评估大表 DDL 成本。ROW 复制中索引仍会影响记录定位和维护成本 |
| 复制线程错误停止、日志缺失或磁盘满 | 线程非正常状态、明确错误码、磁盘告警 | 按错误根因修复；若所需 binlog 已被清理或数据已不一致，使用可信的一致性备份/克隆重新构建副本，再接续复制并验证数据 |

**不要把跳过事务、重置复制位点、删除 relay log 或降低刷盘安全级别作为通用提速方案。** 跳过事务可能制造静默不一致，重置或删日志可能破坏恢复所需信息，降低持久化保障会改变故障丢数据风险；应依据明确根因和经过验证的恢复方案处理。

#### 21.6 读写分离下，如何保证“写后立刻读到”？

1. **写后读主**：对刚完成写入的关联请求读主库，适用于需要读到该写入的业务；主库读取仍应使用正确的事务边界，避免复用旧快照。固定若干秒后切回从库只是经验策略，无法保证异常期间一定追平。
2. **按本次事务的 GTID 等待**：在启用 GTID 且能可靠获取该事务 GTID 的系统中，将其传给准备承担读请求的副本，在同一目标副本上执行等待：

   ```sql
   -- 用本次写入的实际 GTID 集合替换示例参数，超时单位为秒
   SELECT WAIT_FOR_EXECUTED_GTID_SET('source_uuid:transaction_id', 1);
   ```

   返回 0 表示等待成功，1 表示超时；异常或超时时按业务要求回主、重试或返回可重试错误。前提是目标表确实参与复制且数据一致，GTID 已执行本身不能证明被过滤的表数据也已同步。成功后在该副本使用新的读快照查询，防止路由到另一台副本或继续读旧快照。等待应设置短超时并限制并发，避免延迟时大量请求堆积。
3. **允许最终一致性**：对于统计、推荐等可容忍旧数据的场景，明确可接受的新鲜度与降级行为；不能将余额、库存决策等正确性要求简单交给延迟较低的副本。

半同步复制通常等待至少一个副本确认收到并按协议持久化相应日志，**不代表该事务已在副本回放完成并对查询可见**，因此不能单靠半同步解决写后读问题。故障切换时还需核实候选副本已执行的事务及数据完整性，不能仅凭一个延迟值决定提升主库。

#### 21.7 如何判断恢复，以及防止复发？

- 持续观察接收和执行位点、GTID、worker 错误、relay log 占用趋势与心跳，确认接收/回放能够持续跟上新增写入，业务关键读也已恢复；不是看到一次延迟为 0 就结束。
- 粗略估算追赶时间：`待回放量 ÷（回放速率 − 新增日志速率）`，前提是单位一致且速率相对稳定；若回放速率不高于新增速率，积压不会自行消失。事务执行成本差异很大，仅按字节估算只能作为容量参考。
- 恢复读流量和批任务时逐步放量，持续监控，避免刚追平又积压；涉及复制错误、跳过记录或重建时，还需执行适当的数据一致性校验。
- 建立线程停止、业务新鲜度、积压增长、磁盘空间与资源饱和告警；设置大事务/长事务治理规则，做好批任务限速、容量规划、binlog 保留与副本重建演练。

**面试回答示例：**“我会先确认受影响的副本和业务，把关键的写后读请求切到容量允许的主库，同时限制非核心任务。然后查看复制线程状态、错误、主从位点和 GTID，区分是日志接收慢还是回放慢，不能只看 `Seconds_Behind_Source`。接收慢查网络、主库发送与从库落盘，回放慢查大事务、锁等待、worker 并行度、索引和资源争抢。根据证据限速批任务、解除阻塞、优化事务或扩容，必要时重建异常副本；最后用位点趋势、心跳和业务探针确认追平，逐步恢复流量并补充告警。”
